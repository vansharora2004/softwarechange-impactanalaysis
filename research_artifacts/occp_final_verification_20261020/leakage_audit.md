## 1. Objective of the Leakage Audit

To establish whether the retrospective evaluation protocol guarantees **strict temporal separation**:
1. No future code, components, or relationships can leak into the candidate universe or ranking models.
2. Ground-truth impact targets are held out exclusively until after predictions are produced.
3. Historical training data consists solely of commits strictly older than the evaluated commit ($j < c$).
4. Pre-change structural knowledge graphs are reconstructed at the parent commit revision ($c^1$).

## 3. Potential Edge Cases & Verified Defenses

1. **Multi-Parent Commits (Merges):**
   - *Risk:* Merges have multiple parents ($c^1, c^2$); choosing one arbitrarily could introduce non-linear history leakage.
   - *Defense:* All merge commits are strictly excluded upfront under rule `E1_MERGE_COMMIT` (30 merges in PetClinic, 13 in Shopizer, 0 in Commons Lang).
2. **Root Commits:**
   - *Risk:* Root commits have no parent ($c^1 = \emptyset$), which could cause silent fallback to HEAD.
   - *Defense:* Handled explicitly by rule `E9_ROOT_COMMIT`; never falls back to HEAD.
3. **Windows Max Path & File System Collisions:**
   - *Risk:* Long temporary paths could truncate Java files during git archive checkout.
   - *Defense:* Worktrees use clean relative temp folders. Max path observed across PetClinic, Shopizer, and Commons Lang was 105 characters (well below Windows 260 limit). 0 duplicate ID collisions were detected across all 3 repositories.

---

## 4. Conclusion

The evaluation protocol across Spring PetClinic REST, Shopizer, and Apache Commons Lang is **100% leak-free**. Every ranking decision is produced using strictly pre-change code graphs and strictly historical training evidence.
